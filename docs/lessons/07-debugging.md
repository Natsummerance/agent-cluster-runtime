# 07-debugging —— 3 次即停协议（所有修复尝试的硬规则）

> 何时加载：**任何修复尝试之前**。本协议是为了终结「无脑换招重试、一轮一轮烧 token」的循环。

## 协议（强制）
1. **同一问题修复尝试 ≤3 次**。每次尝试 = 一次假设 → 一次改动 → 一次验证。
2. 第 3 次仍失败 → **必须停止**：
   - 跑 `scripts/troubleshoot.ps1` 收集证据（端口/进程/缓存/venv/CI run 状态）；
   - 对照 `docs/lessons/` 索引加载相关模块，逐条匹配已知根因；
   - 形成书面「现象 → 证据 → 根因假设 → 验证计划」，才允许下一次修复。
3. **禁止**：同一问题用不同参数/不同命令连续重试而不诊断；失败后直接换一个方向继续试。
4. 成功经验必须回写对应模块（随提交一起提交）。

## 为什么（本项目真实案例）
- e2e 端口竞态曾连烧 5+ 轮 CI：每轮只改一处就重跑，最后停下来把 playwright 源码、
  配置、日志放一起看，一次定位「探测是单次检查 + curl 探活没带认证头」两个根因。
- 「加载经验库后检查一遍就找到原因」——先查已知问题清单，比盲试快一个数量级。

## 诊断步骤清单（第 3 次失败后执行）
1. 现象复述：什么命令、什么输出、什么时候开始失败。
2. 证据收集：`scripts/troubleshoot.ps1`（本地）或 CI 的 `diagnostics-*` artifact / 失败 job 日志尾部。
3. 已知根因匹配：按场景查 `docs/lessons/` 模块（CI→03、测试→02、release→04……）。
4. 最小复现：本地重跑一次，确认是否必现（区分环境偶发与逻辑错误）。
5. 根因陈述 + 修复方案 + 验证方式，然后才动手。
