# 2025–2026 AI 编码/代理产品「桌面与本地工作台」形态调研报告

> 用途：为 agent-cluster-runtime v0.6.0 的桌面壳、WebSocket 实时通道与多平台打包决策提供竞品依据（当前基线：Electron + React + 内嵌 Python 后端，NSIS Windows 安装包）。
> 调研日期：2026-08-13（北京时间）。方法：纯 Web 检索（仅联网检索与页面打开），未读取本地代码。
> 证据优先级：官方文档/官方仓库 > 权威开发者与技术博客 > 论坛/社区项目 > 镜像与聚合站点；优先采用 2025-06 之后的证据；单一来源信息已标注「未交叉验证」。
> 覆盖产品：Claude Desktop / Claude Code on desktop、Codex desktop app、Cursor、Windsurf、OpenClaw、Goose (Block)、Gemini CLI + vscode-ide-companion、OpenHands desktop、Devin（本地形态），以及 seren、ClawWork、agenttray 等辅助样本（共 12 个样本，满足至少 5 个的要求）。

## 0. 执行摘要

- 架构：商业 AI 桌面产品仍以 Electron 为主（Claude Desktop、Codex、Cursor/Windsurf 基座），但 2026 出现官方级 Tauri 迁移案例（Goose 于 2026-04 从 Electron 迁 Tauri）。主流产品将「桌面壳」与「本地后端」分离，后端以本地服务进程 + WebSocket 控制面暴露（Codex app-server `ws://127.0.0.1:9234`、OpenClaw gateway `ws://127.0.0.1:18789`）——与 v0.6.0 现有架构同构。
- 实时：云端模型流式仍以 SSE 为准，但其 abort/断连/超时问题密集（Claude Code 多个 issue）；本地控制面普遍用 WebSocket；取消/打断正从「断连推断」转向「显式命名信号」（Ably 2026-06）。MCP 三传输（stdio / Streamable HTTP / SSE）成为工具连接标准，ACP 成为新兴客户端协议。
- 分发：Windows 社区 AI 工具事实标准仍是 NSIS EXE；MSIX 仅官方商店产品采用且自更新事故频发。Linux 主流是 AppImage 起步、再补 deb/rpm（Cursor 2025-08 官方化）；Claude Desktop 官方 Linux .deb 迟到 2026-06-30。macOS 公证必须覆盖最终更新产物（seren 反例）。
- 更新：electron-builder + electron-updater + GitHub Releases 是默认路径；Tauri 用 tauri-plugin-updater + minisign。灰度百分比/自动回滚公开证据缺失。
- i18n：FormatJS（react-intl）+ ICU + JSON 是共识架构；Codex 内置 zh-CN 6,161 条翻译仍因「开关默认关闭 + 覆盖不全」被大量投诉——「资源在但体验差」是 2026 竞品普遍状态。
- 桌面集成：Claude Desktop 的全局快捷键 + 托盘最成熟；Codex 连「最小化到托盘」都没有（官方 issue #24678）；第三方托盘工具（agenttray、AgentBar、AgentDiode）在 2026 集中出现，证明该需求真实且未被官方满足。

## 1. 桌面壳架构模式

### 1.1 壳与后端分离：本地服务进程 + WebSocket 控制面成为主流

- Codex app：2026-02-02 发布 macOS 桌面应用，本质是给 Codex CLI agent 套桌面 UI（来源：Simon Willison《Introducing the Codex app》，https://simonwillison.net/2026/Feb/2/introducing-the-codex-app/ ，2026-02-02，可信度：权威开发者博客）。其本地后端为 app-server：负责 thread/session/工具执行的本地服务，客户端以 JSON-RPC 交互；生产模式为 JSONL over stdio，实验模式为 `ws://127.0.0.1:9234`（来源：openai/codex 官方仓库 codex-rs/app-server README，https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md ，持续维护，可信度：官方仓）。
- 2026-07 官方 PR #35098 已为 app-server 增加远程 code-mode 主机支持（跨线程共享 WebSocket 连接、Bearer 认证与健康检查），即「本地壳 ↔ 远程后端」切换能力进入主分支（来源：https://github.com/openai/codex/pull/35098 ，2026-07-23，可信度：官方仓）。社区部署文章确认 stdio 为唯一生产模式、WS 为实验模式（来源：https://codex.danielvaughan.com/2026/03/28/codex-app-server-remote-deployment/ ，2026-03-28，可信度：社区技术博客）。
- OpenClaw：本地网关进程以 `ws://127.0.0.1:18789` 提供控制面，桌面/CLI/Control UI 均为该网关的 WebSocket 客户端（来源：官方仓 issue https://github.com/openclaw/openclaw/issues/43886 ，2026-03-11，可信度：官方仓；官方文档 Control UI，https://docs2.openclaw.ai/web/control-ui ，2026-08-01，可信度：官方文档）。第三方桌面壳 ClawWork 即通过 OpenClaw Gateway 的 WebSocket API 工作（来源：https://github.com/clawwork-ai/ClawWork/blob/main/AGENTS.md ，2026-03-11，可信度：官方仓；另见 https://www.sourcepulse.org/projects/26715241 ，无日期，可信度：低，未交叉验证）。
- Gemini CLI + IDE 伴侣：CLI 与 IDE 插件通过「本地 MCP over HTTP 服务器」通信，端口动态分配（监听端口 0），单端点 /mcp——「CLI 为后端、IDE 为前端」的又一壳-后端分离样本（来源：官方规范 https://geminicli.com/docs/ide-integration/ide-companion-spec/ ，2025-09-14，可信度：官方文档；仓库版 https://github.com/google-gemini/gemini-cli/blob/3502249e0caf6fa4082da6173f1fab16580de923/docs/ide-integration/ide-companion-spec.md ，2025-09-15，可信度：官方仓）。

### 1.2 技术栈：Electron 仍是商业默认，Tauri 2026 出现官方级迁移

- Electron 阵营：Claude Desktop 为 Electron 应用（社区 Linux 移植项目明确记录，来源：https://github.com/lhl/claude-desktop-arch ，持续更新，可信度：社区项目，中等）。Cursor/Windsurf 基于 VS Code fork（Electron/Code OSS 基座；官方文档未直接声明技术栈，属行业共识，未交叉验证）。
- Tauri 阵营：Goose 官方宣布 Goose 2.0 beta 桌面从 Electron 迁移到 Tauri，理由为性能提升与 UI 刷新，并统一改用 ACP（Agent Client Protocol）作为客户端与 goose 服务之间的协议（来源：官方博客《goose 2.0 beta - new architecture and clients》，https://goose-docs.ai/blog/2026/04/08/goose-acp-and-new-tui/ ，2026-04-08，可信度：官方博客）；迁移计划此前已在讨论区公开（https://github.com/aaif-goose/goose/discussions/7309 ，2026-02-17，可信度：官方仓）。
- 趋势判断：2025–2026 尚无头部商业产品仅为「减小包体积」换栈的先例；Goose 迁移的理由集中在性能/内存与协议重构。v0.6.0 若 Electron 工程已成型，迁移 Tauri 的收益需用内存/启动指标论证，不建议仅因趋势换栈。

### 1.3 本地 / 远程 / 云端形态

- Codex：本地 app-server（本地工具执行与沙箱）为默认；2026-07 起支持远程 code-mode 主机（见上文 PR #35098）。
- OpenHands：传统形态是 Docker/uv 启动的本地 Web 工作台（http://localhost:3000），并非独立桌面壳（来源：https://www.kdnuggets.com/openhands-open-source-ai-software-developer ，2025-02-25，可信度：媒体，中等；fork 仓库 README，https://github.com/muffy86/OpenHands ，2026-04-13，可信度：社区，低）。2026 年其「Agent Canvas」开始发布 .exe/.dmg 安装包（来源：https://sourceforge.net/mirror/openhands/activity/ ，2026 年，可信度：镜像站，低）→ OpenHands 桌面壳仍属早期。
- Devin：以云端工作区 + IDE 扩展/CLI 接入为主，未检索到独立桌面壳的公开证据 → 数据不足。

**对 v0.6.0 的启示**

1. 保持「壳与后端分离」并明确协议边界：把内嵌 Python 后端升级为可独立启动、可远程替换的 app-server（对齐 Codex/OpenClaw），壳只负责 UI、状态订阅与指令下发。
2. 后端通道优先级参考 Codex：本地进程间用 stdio/管道保证生产可靠性，WebSocket 作为多客户端/远程控制面；v0.6.0 可两者并存、用特性开关切换。
3. 学 Goose 预留协议化路线：私有 JSON-RPC 先跑通，未来向 MCP/ACP 映射，为 CLI/IDE/TUI 多端复用铺路（与本项目 agent-cluster 多 agent 定位直接相关）。

## 2. 实时交互技术

### 2.1 SSE 的地位与坑

- SSE 仍是云端模型流式输出的默认：但其运维问题在 2025-06 之后密集暴露于 Claude Code 官方仓：
  - 流式挂起无超时、ESC 无法彻底取消并自动重启队列（https://github.com/anthropics/claude-code/issues/33949 ，2026-03-12，可信度：官方仓，未交叉验证）；
  - MCP Streamable HTTP 的 SSE 重连回归，约 60 秒掉线一次（https://github.com/anthropics/claude-code/issues/38631 ，2026-03-24，可信度：官方仓）；
  - 长工具执行期间 SSE 静默，被企业代理 60–120 秒空闲超时断连（https://github.com/anthropics/claude-code/issues/45224 ，2026-04-07，可信度：官方仓）；
  - MCP 超时配置在 Streamable SSE/HTTP 连接上被忽略（https://github.com/anthropics/claude-code/issues/20335 ，2026-01-22，可信度：官方仓）。
- 结论：SSE 的 abort/drop 处理必须显式设计——心跳/keep-alive、超时、幂等重连、取消，缺一不可。

### 2.2 WebSocket 作为本地控制面

- Codex app-server（`ws://127.0.0.1:9234`，实验）与 OpenClaw gateway（`ws://127.0.0.1:18789`，生产）都选择 WebSocket 作为本地壳↔后端的双向通道（来源见第 1 节）。
- Ably 2026-06-24 专文《Stop vs disconnect》：取消应是「命名信号」而非「从断连推断」；在其会话模型上，cancel 是客户端显式发布的事件（activeRun.cancel() / session.cancel(runId)）（来源：https://ably.com/blog/stop-vs-disconnect-canceling-ai-streaming ，2026-06-24，可信度：供应商技术博客，中高）。
- Ably 同时指出 Vercel AI SDK 的 stop() 并不真正取消流——修复方案是双向通道 + 显式取消消息（来源：https://ably.com/vercel/why-vercel-ai-sdk-stop-doesnt-cancel-the-stream ，2026-05-05，可信度：供应商技术博客，中高）。SSE 单向管道上，取消唯一手段是断开，而断开与网络抖动无法区分；定向取消需带句柄（来源：https://ably.com/blog/ably-ai-transport-sdk-realtime-streaming-session-continuity ，2026-04-29，可信度：供应商技术博客，中高）。

### 2.3 MCP 传输三分天下 + ACP 登场

- Windsurf 官方支持 MCP 三种传输：stdio、Streamable HTTP、SSE，且每种支持 OAuth（来源：https://docs.windsurf.com/zh/windsurf/cascade/mcp ，持续更新，可信度：官方文档）。
- Gemini 的 IDE 伴侣规范将「本地 MCP over HTTP」定义为插件唯一传输（来源见 1.1，2025-09-14，官方文档）。
- Goose 于 2026-04 宣布 ACP 成为 goose 客户端的新默认协议，官方桌面/TUI 共用同一协议与服务器（来源：https://goose-docs.ai/blog/2026/04/08/goose-acp-and-new-tui/ ，2026-04-08，可信度：官方博客）。
- 实时打断/注入的 UX 现状：Claude Code v2.1.77 变更日志记录 ESC 在非流式请求上的改进（见 #33949 引述，2026-03-12，官方仓）；业界正转向「取消带 run/task id 的显式消息 + 可定向中断」，替代「断开即取消」。

**对 v0.6.0 的启示**

1. v0.6.0 规划 WebSocket 实时通道方向正确：本地控制面用 WS，取消/打断做成显式消息（cancel 携带 task id），不要依赖断连推断；云端模型流仍用 SSE，但必须加心跳、超时与幂等重连。
2. 若暴露 MCP 能力，优先 stdio（本机）+ Streamable HTTP（多客户端），SSE 仅作兼容层。
3. 打断语义要区分「停止当前生成」与「回滚已执行副作用」，这是 2026 竞品正在补的课，可作为差异化卖点。

### 3.2 macOS 签名/公证的实战教训（seren 反例）

- updater 下发未公证的 .app.tar.gz，被 Gatekeeper 拒为损坏（来源：https://github.com/serenorg/seren-desktop/issues/1244 ，2026-03-21，可信度：社区仓库，中高，与下方 issue 相互印证）。
- arm64/x64 生成同名 updater 产物，上传冲突导致全平台发布失败（来源：https://github.com/serenorg/seren-desktop/issues/493 ，2026-02-09，可信度：社区仓库，中高）。
- 捆绑 MCP 服务器 node_modules 中的未签名二进制导致 Apple 公证连续失败，多版本未公证（来源：https://github.com/serenorg/seren-desktop/issues/968 ，2026-03-04，及 https://github.com/serenorg/seren-desktop/issues/1001 ，2026-03-06，可信度：社区仓库，中高）。
- 结论：公证必须覆盖「最终分发的更新产物」而非仅首装 DMG；双架构产物须独立命名；任何随包携带的本地二进制（含 Python 后端！）都必须签名——这对 v0.6.0 内嵌 Python 后端的 macOS 打包是直接警示。

### 3.3 平台格式小结

- Linux：头部产品路线一致——先 AppImage，后补 deb/rpm（Cursor 2025-08 官方化、Claude 2026-06 仅 deb）。未观察到任何主打产品提供 Flatpak → Flatpak 可暂缓。
- Windows：社区 AI 工具事实标准为 NSIS（ClawWork 等）；MSIX 只有官方商店产品（Claude、Codex）使用，且自更新受限（见第 4 节）。
- macOS：x64/arm64 双架构为标配（Cursor 社区包、Claude Linux beta 均双架构）；签名/公证链要覆盖安装包与更新包。

**对 v0.6.0 的启示**

1. 保持 NSIS 作为 Windows 主分发（社区事实标准）；MSIX 仅作为商店渠道二期，且不要在其上做自更新。
2. macOS 若立项：DMG + 公证 + 每架构独立命名的更新产物；内嵌 Python 解释器与依赖必须一并签名，避免 seren 式公证失败。
3. Linux 首包选 AppImage（Cursor 路线），再补 deb/rpm 覆盖 Debian/Fedora 系；Flatpak 不做。

## 4. 自动更新

### 4.1 Electron 路线（v0.6.0 当前栈的最优解）

- electron-builder 的 electron-updater 开箱支持 GitHub Releases、S3、DigitalOcean Spaces、Keygen 与通用 HTTP(S) 作为更新源；私有仓库可经 GH_TOKEN 使用 GitHub API（来源：https://www.electron.build/docs/features/auto-update/ ，持续更新，可信度：官方文档；中文镜像同内容，https://builder.electron.js.cn/auto-update ，持续更新，可信度：官方文档镜像）。
- 社区 AI 桌面项目的标准姿势即「electron-updater + GitHub Releases，主进程 autoUpdater，可用/下载中/就绪三态通知 UI，任务运行中延迟重启」（来源：https://github.com/rioX432/live-translate/issues/314 ，2026-03-23，可信度：社区仓库，中低，为典型实践样本）。

### 4.2 Tauri 路线

- tauri-plugin-updater：更新清单 latest.json + minisign 签名校验，endpoints 指向 GitHub Releases（来源：官方插件文档 https://v2.tauri.app/plugin/updater/ ，持续更新，可信度：官方文档；实例：https://raw.githubusercontent.com/alecdotdev/Markpad/master/RELEASING.md ，持续更新，可信度：社区仓库）。
- 实践样本：SwarmNote 用「UpgradeLink 主源 + GitHub Releases 备用，minisign 签名，强制/可选更新两种策略」双通道灰度（来源：https://github.com/swarm-apps/SwarmNote/issues/47 ，2026-03-31，可信度：社区仓库，中低）；HyperionBox 的桌面端（Windows/Linux AppImage）用 Tauri updater + minisign + latest.json（来源：https://deepwiki.com/GoodDay360/HyperionBox/16-auto-update-system ，2026-02-13，可信度：AI 代码解读站，中低）；vibe 同样配置 GitHub Releases endpoint 与 pubkey（来源：https://deepwiki.com/thewh1teagle/vibe/5.3-auto-update-system ，2025-11-13，可信度：AI 代码解读站，中低）。

### 4.3 反例：MSIX 自更新事故链（Claude Desktop）

- 2026 年 5 月至 8 月，Claude Desktop Windows MSIX 的自动更新持续出现严重事故（均为官方仓 issue，可信度：官方仓）：
  - AppContainer Job 竞争导致更新后无法启动，且升级时在途会话永久孤儿化（https://github.com/anthropics/claude-code/issues/59934 ，2026-05-16）；
  - 更新器写入自身包目录破坏 MSIX 完整性，包状态卡在 Modified/NeedsRemediation，重装无效（https://github.com/anthropics/claude-code/issues/68909 ，2026-06-15）；
  - 应用内更新无限「Downloading update…」（MSIX 上自更新被禁用后的状态错乱）（https://github.com/anthropics/claude-code/issues/81003 ，2026-07-23）；
  - 更新重试指向已删除的 %TEMP% 包导致应用不可启动且不可修复（https://github.com/anthropics/claude-code/issues/83612 ，2026-08-02）；
  - 失败回滚对正式签名包使用 PreserveApplicationData，导致应用自我损坏（https://github.com/anthropics/claude-code/issues/83854 ，2026-08-03）。
- 官方 Linux .deb 干脆不提供自动更新（korben.info，2026-06-29，见 3.1），apt 仓库版才走包管理器更新。

**对 v0.6.0 的启示**

## 附注：对 v0.6.0 的总体建议（一句话版）

沿用 Electron 壳 + 本地后端分离（把 Python 后端定义为 app-server，WS 控制面 + stdio 备用）；Windows 保持 NSIS + electron-updater/GitHub Releases + Stable/Early 双通道；Linux 先 AppImage 后 deb/rpm；macOS 若上则公证覆盖更新产物与内嵌 Python 运行时；i18n 用 react-intl + ICU + JSON 并保证 zh-CN 默认可用；托盘/全局快捷键/通知作为差异化优先投入。
