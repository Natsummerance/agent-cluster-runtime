## 维度 2：预算与成本治理

### 2.1 模型厂商原生能力

- OpenAI：提供 organization / project 两级月度硬性 spend limit + 阈值预警（spend alerts），并经 Admin API / Terraform 管理（如 openai_project_spend_alert 资源）；注意 spend alerts 只通知不拦截，硬拦截由 spend limits 承担。（OpenAI 官方文档「Spend limits」「Admin APIs」「Rate limits and spend with Terraform」，访问于 2026-08-13，★高）https://developers.openai.com/api/docs/guides/spend-limits https://developers.openai.com/api/docs/guides/admin-apis https://developers.openai.com/api/docs/guides/terraform/rate-limits-and-spend
- Anthropic：API 侧采用预付费额度 + 按模型/tier 的速率限制，Console 有 Limits 页；帮助中心提供成本与使用报告（2026-03-04 更新）；Claude Code 组织级有 Analytics dashboard（采用度排行榜、每用户支出）与免费 Analytics API（按模型估算成本与 token）。未发现与 OpenAI 同形态的「月度硬性 spend cap」公开文档（数据不足）。（Anthropic 官方文档/帮助中心/Claude Docs，★高）https://platform.claude.com/docs/en/api/rate-limits https://support.anthropic.com/en/articles/9534590-cost-and-usage-reporting-in-console https://code.claude.com/docs/zh-TW/admin-setup https://docs.claude.com/en/api/claude-code-analytics-api

### 2.2 网关预算治理（企业内部落地方式）

- LiteLLM 是事实上的预算治理组件：proxy 支持 per-key / per-user / per-team 的 max_budget + budget_duration（周期重置），并有 Budget Manager 编程接口；Cline 社区实践即「Cline 直连 LiteLLM，用 max_internal_user_budget: 3500 等配置做预算池」。（LiteLLM 官方文档，★高；cline/cline#2106，2025-03-04，★中）https://docs.litellm.ai/docs/proxy/users https://docs.litellm.ai/docs/budget_manager https://github.com/cline/cline/issues/2106
- Cline 本身无预算治理产品能力（仅单次请求的 thinking/token 预算滑动条），治理必须外挂网关——「编辑器具预算治理」仍是产品空档。（cline/cline#8342，2025-12-29，★中）https://github.com/cline/cline/issues/8342

### 2.3 「预算池」现成产品：Databricks Unity AI Gateway Budgets（旗手）

- 2026-07-22 官方公告「Introducing AI spend controls with Unity AI Gateway」：以 Budget 资源跨模型/代理/提供方做统一支出控制，支持共享阈值 + 每用户 override、按 workspace/资源标签限定范围、超限自动停止支出。（Databricks 官方博客，2026-07-22，★高）https://www.databricks.com/blog/introducing-ai-spend-controls-unity-ai-gateway
- 官方文档（2026-08-02 更新）：每个预算最多 4 个共享阈值 + 20 个每用户 override，账户最多 1000 个预算，追踪 pay-per-token 与 ai_query（批处理）推理支出。（★高）https://docs.databricks.com/aws/en/ai-gateway/budgets
- 2026-07-27 官方实践博客「How Databricks manages its own coding agent spend with Unity AI Gateway Budgets」三条工程教训：防失控硬闸与月度预算分开设置；多数限额命中应自服务解锁；审批只留给真正例外且带时限。（★高）https://www.databricks.com/blog/how-databricks-manages-its-own-coding-agent-spend-unity-ai-gateway-budgets
- 产品页 2025-09-07 即提出「预算阈值触达时自动停止 AI 支出」的产品愿景。（★高）https://www.databricks.com/product/artificial-intelligence/unity-ai-gateway

### 对 v0.6.0 的启示

- 「预算池」已从概念变成 GA 产品形态（Databricks Budgets，2026-07）：v0.6.0 最低可行治理 = 硬上限 + 阈值预警 + 按项目/用户分账，三者分别对应防失控、可预见、可归责。
- 直接采用 Databricks 的实践教训：防失控上限与月度预算分开；超限解锁尽量自服务；审批带时限。

## 维度 4：OAuth MCP 与远程 MCP 标准化

### 4.1 规范演进时间线（2025-03-26 之后）

- 2025-03-26：OAuth 2.1 + PKCE 首次进入 MCP 规范；授权可来自服务器自实现的授权服务器或外联授权服务器；同版启动 stdio/SSE → Streamable HTTP 的传输替换。（MCP 官方 changelog，2025-03-26，★高）https://modelcontextprotocol.io/specification/2025-03-26/changelog/ ；ironclaw 文档镜像（★中）https://docs.rs/ironclaw/latest/ironclaw/tools/mcp/auth/index.html
- 2025-06-18：SSE 传输正式弃用，Streamable HTTP 成为推荐远程传输，并补充弹性连接定义。（MCP 官方 transports 文档，2025-06-18，★高）https://modelcontextprotocol.io/specification/2025-06-18/basic/transports ；社区迁移讨论（kafka-schema-reg-mcp issue #38，★中）https://github.com/aywengo/kafka-schema-reg-mcp/issues/38
- 2025-11-25：与 RFC 9728（Protected Resource Metadata）对齐——WWW-Authenticate 变为可选 + .well-known 元数据发现；新增 OIDC Discovery 1.0、Client ID Metadata Documents（CIMD）、增量 scope 同意。（MCP 官方 changelog，2025-11-25，★高）https://modelcontextprotocol.io/specification/2025-11-25/changelog/
- 2026-07-28（第五版规范）：核心默认无状态（stateless by default）、HTTP transport 默认无状态、多项扩展毕业转正；Claude 官方博客 2026-07-27 发布致谢文；.NET MCP C# SDK 2.0 与 Cloudflare 同日跟进。（★高）https://claude.com/blog/bringing-mcp-2026-07-28-to-claude https://devblogs.microsoft.com/dotnet/announcing-v20-of-the-official-mcp-csharp-sdk/ https://developers.cloudflare.com/changelog/post/2026-07-28-cloudflare-mcp-servers-mcp-2026-07-28/
- 重要勘误：用户提问中的「RFC 9626」实为《Deprecation HTTP Header Field》，与 MCP 授权无关；MCP 授权实际引用 RFC 9728（Protected Resource Metadata），并依赖 RFC 8707（Resource Indicators）与 RFC 8414（OAuth 2.0 Authorization Server Metadata）。（RFC Editor 官方页面，★高）https://www.rfc-editor.org/rfc/rfc9626.html

### 4.2 实际采用：OAuth 化远程 MCP 已进入头部产品

- GitHub 官方托管 GitHub MCP server：OAuth 认证 + 自动更新，是「远程 MCP 官方化」标杆。（GitHub 官方博客，2025-07-29，★高）https://github.blog/ai-and-ml/generative-ai/a-practical-guide-on-how-to-use-the-github-mcp-server/
- Claude Desktop / Connectors 将 OAuth 作为远程连接器的认证要求。（Claude 官方文档，2026-07，★高）https://claude.com/docs/connectors/building/authentication ；Anthropic 中文帮助中心连接器目录 FAQ（2026-04）https://support.claude.com/zh-CN/articles/11596036-anthropic-连接器目录常见问题解答
- 模板生态跟进：Railway「远程 MCP 服务器模板（Remote Streamable）」即用 OAuth 2.1 示例。（Railway 部署模板页，2026-07，★中）https://railway.com/deploy/mcp-server-starter-or-remote-streamable-
- 互操作摩擦（未交叉验证）：DCR 在规范中为 SHOULD，官方 rust-sdk 专门提交 PR 将动态客户端注册实现为可选以对齐 RFC 8414；社区实践显示部分客户端「预期开放 DCR」而多数 IdP 不提供；第三方实测 ChatGPT Web 的 OAuth 2.1 + DCR 可完整走通。（rust-sdk PR #463，2026-02-18，★中）https://github.com/modelcontextprotocol/rust-sdk/pull/463 ；dev.to 实测文（2026-01-29，☆低，未交叉验证）https://dev.to/playfulprogramming/securing-mcp-servers-with-oauth2-ory-hydra-claude-code-chatgpt-58hm ；dev.to IdP 桥接文（2026-05-14，☆低，未交叉验证）https://dev.to/velias/bridge-the-gap-between-your-idp-and-the-mcp-world-3gbn
- 未实现 OAuth 的旧式服务端进入弃用方向：@modelcontextprotocol/server-legacy（npm，2026-07-20，☆低，未交叉验证）https://www.npmjs.com/package/@modelcontextprotocol/server-legacy

### 对 v0.6.0 的启示

- OAuth MCP 已从差异化能力变成入场券：v0.6.0 应按 2025-11-25+ 授权栈实现（OIDC Discovery 1.0、RFC 9728 .well-known 元数据、CIMD、PKCE 必需、RFC 8707 resource indicators 必需）。
- 远程 MCP 客户端能力优先于自建 MCP 网关：GitHub/Claude Desktop/Cloudflare 已从 provider 侧收编远程 MCP，v0.6.0 的主路径应是「OAuth 客户端 + Streamable HTTP」，而不是自研网关协议。
- DCR 实现为可选并兼容 IdP 缺失 DCR 的现状，避免与主流企业 IdP 互操作失败。

- 社区 WebSocket 传输增强提案 SEP PR #1287 长期未合入。（★中）https://github.com/modelcontextprotocol/modelcontextprotocol/pull/1287
- SSE 弃用节奏：2025-06-18 官宣弃用，计划 2026-03-26 完全移除（Forge-Space mcp-gateway issue #153 记录，★中）https://github.com/Forge-Space/mcp-gateway/issues/153
- 关于「Cloudflare 2026 弃用 SSE」：未找到官方公告，不采纳该说法（数据不足）。

### 6.2 通用实时通道建议（与 MCP 无关的第三方指南）

- 2026 年通用建议仍是：单向服务端推送起步用 SSE（浏览器原生、自动重连）；客户端需要高频双向发送时用 WebSocket；AI 聊天接口推荐 SSE（Vercel AI SDK 路线）。（pkgpulse 指南，2026-03-08，☆低，未交叉验证）https://www.pkgpulse.com/blog/sse-vs-websocket-vs-long-polling-real-time-2026
- Cloudflare 代理下 SSE/WebSocket 超时行为指南（stackharbor，2026-07-02，☆低，未交叉验证）https://stackharbor.com/en/knowledge-base/cffix-websockets-sse-behind-cloudflare/

### 对 v0.6.0 的启示

- WebSocket 不是 MCP 生态的标准方向：v0.6.0 不应把 WS 作为对外互操作通道，主路径应为 Streamable HTTP（含 SSE 事件流）。
- 若确有双向高频控制面需求，可作为私有扩展另立通道，但需接受「非标准、需自维护」的成本。
- 已存在的 SSE 实现应尽快收敛到 Streamable HTTP，跟随官方 2026-03-26 完全移除 SSE 的时间表。
