## 一、项目级 / 多会话 / 多任务编排

**1. LangChain：目前「项目层管理」最完整的实现**
- [LangGraph Platform GA 官方博客](https://www.langchain.com/blog/langgraph-platform-ga)（2025-05-14，官方博客）：GA 时即提供约 30 个 API 端点、一键部署，持久化层同时支撑 memory、HITL 与多 agent 异步协作；企业版含 RBAC 与 workspaces；提供 agent registry、assistant 版本管理、Remote Graphs（可被其他项目调用）。2025-10 平台改名 **LangSmith Deployment**。
- [LangSmith threads API 官方文档](https://docs.langchain.com/langsmith/use-threads)（更新于 2026-07-25，官方文档）：`thread_id` 是持久化游标，天然支持「一个项目 = 多个会话 + 共享上下文」；thread 可用 metadata 过滤、关联 `assistant_id` 与 cron 任务，本质上就是项目看板所需的数据模型。

**2. CrewAI AMP：组织级 Agent 运营平台**
- [CrewAI AMP 发布博客](https://crewai.com/blog/crewai-amp---the-agent-management-platform)（2025-10-01，官方博客）：定位 Agent Operations Platform，Studio 低代码构建后可下载为代码；含 RBAC 与审计日志；官方披露企业规模数据（15 天 10 万+ 执行、近 50 万 agent 部署），证明其多任务/多租户运营已商用化。

**3. AWS Strands：编排四原语 + 原生托管**
- [AWS Strands 1.0 官方发布博客](https://aws.amazon.com/blogs/)（2025-07-14，官方博客；正文页受抓取限制，细节经 [aws-news.com 转述](https://aws-news.com/article/2025-07-15-introducing-strands-agents-10-production-ready-multi-agent-orchestration-made-simple)（2025-07-15，社区转载）交叉印证）：四原语 **Agent-as-Tool / Handoffs / Swarms（共享内存协作）/ Graphs（确定性编排）**；2025-12-03 宣布 TypeScript 支持（官方公告）。

**4. Microsoft Agent Framework（MAF）1.0：合并 SK + AutoGen 的统一框架**
- [MAF 1.0 GA 官方博客](https://devblogs.microsoft.com/agent-framework/2026/04/)（2026-04-02/03，官方博客）：.NET + Python，语义内核 Semantic Kernel 与 AutoGen 合并（两者转入维护模式）；内置 A2A v1.0 互操作、CodeAct（折叠工具调用轮次）、skills 机制含人工审批脚本。2026-06 Build 大会发布 **Foundry Harness / Hosted Agents GA**（[InfoQ 报道](https://www.infoq.com/)（2026-08-02，知名媒体）），补齐托管与执行环境。

**5. 轻量型 SDK 路线（OpenAI / Anthropic / Google ADK）**
- OpenAI Agents SDK（[官方仓库](https://github.com/openai/openai-agents-python)）：2025-03 开源（Swarm 继任），内置 sessions 会话记忆、handoffs 交接、`max_turns` 上限（默认 10，v0.16.0 于 2026-05-06 改为默认无限制）。
- 这些 SDK 的共性：**框架薄、编排靠宿主**，项目级管理能力依赖外部平台（如 Codex/CI/云平台）。

**6. 开源先驱项目（基线参照）**
- ChatDev 2.0 + Puppeteer：RL 演化编排（[arXiv:2505.19591](https://arxiv.org/abs/2505.19591)，2025）；PyPI `chatdev` SDK + YAML workflow（[GitHub OpenBMB/ChatDev](https://github.com/OpenBMB/ChatDev)）。
- MetaGPT：MGX 发布（2025-02-19），AFlow 论文（2025-01-22），核心开源 2025 年后近乎停滞。**2025–2026 路线图：数据不足。**

**对 v0.6.0 的启示**
- 项目层看板应复制 LangSmith 的「thread 持久化游标 + metadata 过滤 + assistant 版本」模型，作为 v0.6.0 看板与预算池的统一数据底座；「一个项目 = 多个会话 + 共享上下文」已有成熟产品语义可直接对标。
- 任务分解不要只做单一图编排：AWS Strands 四原语提示 v0.6.0 至少区分「确定性流程编排」与「共享内存协作（swarm）」两种协调模式，避免一刀切。
- 完整 PPM（P2）可对标 CrewAI AMP：Studio 可视化 + RBAC + 审计日志是项目层成熟的三个关键标签，缺一即难以自称「项目级平台」。

## 二、预算 / 成本治理

**1. Google「Budget Tracker + BATS」：把预算注入 agent 推理循环（前沿学术）**
- Google 论文（2025-11）提出 Budget Tracker 将剩余 token/工具调用预算注入 agent 推理，BATS 据预算动态调整规划/验证策略；[CIO.com](https://www.cio.com/)（2025-12-11）与 [VentureBeat](https://venturebeat.com/)（2025-12-15）报道（均为知名媒体，互相印证）。属自适应预算最前沿研究，尚未见商用产品化。

**2. Claude Code / Agent SDK：美元硬顶是最清晰的产品级参考**
- `--max-budget-usd`：print 模式美元硬顶，超限返回 `error_max_budget_usd` 错误子类型，另有 `--max-turns`（[Claude Code 官方仓库](https://github.com/anthropics/claude-code)）；Python Agent SDK 的预算支持见 [PR #293](https://github.com/anthropics/claude-agent-sdk-python/pull/293)（2025-10-27，官方仓库/社区贡献）。此能力目前**按会话而非按项目池**计（未交叉验证其项目级聚合能力）。

**3. LangSmith：项目级限额已存在，但语义需注意**
- 项目级 `cost_limit_usd` / `alert_threshold_percent` / `alert_emails`（社区课程页面，标注「Verified April 2026」，社区来源）；官方 FAQ 称限额按 trace 数量而非美元计（官方文档）。即「项目级成本闸门」有真实实现，但美元级精确计量尚未统一（两处来源存在口径差异，标注「未交叉验证」）。

**4. 框架层普遍薄弱（反面证据）**
- CrewAI 仅有 `max_rpm` / `max_iter` 类限制，无原生 token 预算（[dev.to 社区文章](https://dev.to/)（2026-05-03，社区博客）批评其为「钝工具」）；OpenAI Agents SDK 的 `max_turns` 同理。**AG2/AutoGen 原生 token 预算池：数据不足（AutoGen 已入维护模式）。**

**5. 前缀缓存计量（成本治理的重要组成）**
- OpenAI：cached input 5 折（官方文档）；Azure OpenAI Provisioned 部署缓存折扣最高 100%（官方文档）。Anthropic prompt caching 为 90% 折扣、5 分钟 TTL（官方文档，本轮未重新打开复核，标注「未交叉验证」）。
- 社区包 agent-cost-guard（npm，2026-03-22）声称含缓存折扣与 reasoning token 计量（社区来源、低可信、未交叉验证；其附带「11 天 $47K ping-pong」事故传闻不予采信为事实）。

**对 v0.6.0 的启示**
- **预算池是明确的市场空白**：除 Claude Code 的会话级美元硬顶和 Google 论文原型外，几乎无人提供「项目级 token 预算池 + 自适应预算」，v0.6.0 的看板+预算池具备差异化先发机会。
- 实现三件套：项目级美元/额度上限与告警（LangSmith 语义）+ 预算注入推理循环的自适应策略（Google BATS）+ 超限明确报错与恢复语义（Claude `error_max_budget_usd`）。
- 前缀缓存计量列入 P2 时需按 provider 分账：OpenAI 50% / Azure 100% / Anthropic 90% 的折扣机制不同，运行时账本必须区分 cached/uncached 与 reasoning token，否则预算池数字失真。

## 三、审批门与 HITL（人机协同）

**1. LangGraph interrupt：语义最完整的参考实现**
- [官方文档 Human-in-the-loop](https://docs.langchain.com/oss/python/langgraph/human-in-the-loop)（官方文档，本轮已核实原文）：区分**动态 interrupt 与静态 breakpoint**；`checkpointer + thread_id` 实现断点续跑；`Command(resume=...)` 携带人工决策继续执行；审批用 `Command(goto)` 分流 approve/reject；支持工具内部 interrupt；并行多 interrupt 用 `resume_map` 按 id 配对；流式暴露 `stream.interrupts / interrupted`。这是目前开源侧最完整的「中断—续跑—回滚」原语集。

**2. CrewAI Flows：企业审批队列 + 外部系统集成**
- [企业文档 Flow HITL Management](https://github.com/crewAIInc/crewAI/blob/e21c5062/docs/en/enterprise/features/flow-hitl-management.mdx)（2026-02-18 更新，官方企业文档）：待审批队列、超时自动批准、webhooks 对接自定义审批 UI / Jira / ServiceNow。旧版 `human_input=True`（控制台同步阻塞）已明显过时。

**3. OpenAI Agents SDK：approval 模式 + 状态恢复**
- approval 模式暂停 → `result.to_state()` 序列化 → `state.approve()/reject()` → 同一 RunState 续跑；JS 版暴露 `interruptions` 数组（官方仓库文档）。

**4. Anthropic Claude：hooks + 恢复命令**
- `PreToolUse / PostToolUse / Notification / Stop` 四类 hooks，`/checkpoint` 手动打点与 `--resume` 恢复（官方文档/官方博客）。人工纠正还可经 `@human_feedback(learn=True)` 沉淀（见下节 CrewAI 记忆机制）。

**5. 微软 MAF：审批脚本化**
- MAF skills 机制含人工审批脚本（[MAF 官方博客](https://devblogs.microsoft.com/agent-framework/2026/04/)（2026-04，官方博客）），审批门成为技能/工作流的一部分。

**对 v0.6.0 的启示**
- v0.6.0 审批门建议以 LangGraph interrupt 语义为蓝本：动态暂停点 + `thread_id` 断点续跑 + 人工决策携带回执行流；「回滚/断点续跑」已是全行业标配（LangGraph checkpointer、Claude `--resume`、OpenAI `state.approve`），v0.6.0 必须内建而非后补。
- P2 企业集成可对标 CrewAI：审批队列化 + 超时自动批准 + webhook 接 Jira/ServiceNow，是「企业级审批门」与「开发者级 interrupt」的分界线。
- 项目层看板应能展示「哪些会话处于等待审批」：LangGraph 的 `interrupts` 流式暴露方式提示 v0.6.0 需要全局 HITL 状态视图，而非散落在各会话内。

## 四、记忆与进化

**1. CrewAI Cognitive Memory：目前记忆功能最产品化的框架**
- [官方博客](https://crewai.com/blog/)（2026-03-04，官方博客，本轮已核实原文）：**encode / consolidate / recall / extract / forget 五认知操作**；记忆系统本身用 CrewAI Flows 构建；`extract_memories()` 把经验原子化并 SOP 化；矛盾检测与合并（PostgreSQL→MySQL 迁移案例）；recall 置信度不足自动深挖；`@human_feedback(learn=True)` 把人工纠正沉淀为长期经验。官方 docs v1.15.1 给出权重参数（recency 0.3 / semantic 0.5 / importance 0.2、consolidation_threshold 0.85，官方文档）。

**2. LangGraph Store：跨线程长期记忆的标准分层**
- [官方文档](https://docs.langchain.com/oss/python/langgraph/memory)（2026-06-10，官方文档）：Store 提供**跨线程**长期记忆，与 checkpointer（每线程短期状态）分离——这正是「项目共享上下文」的正确架构分层；后端支持 Redis / Postgres / Mongo（[MongoDB 官方博客](https://www.mongodb.com/blog)（2025-08）佐证）。

**3. Letta：自编辑记忆 + sleep-time compute**
- 记忆块（memory blocks）自编辑、**sleep-time compute**：空闲时后台 agent 异步整合记忆（[官方博客](https://www.letta.com/blog)（2025-04-20，官方博客））；Claude memory omni-tool（2025-09-30，官方公告）；「Our Next Phase」提出 git 背书的记忆投影、sleep-time 从服务端转向客户端 subagent（[官方博客](https://www.letta.com/blog)（2026-03-15，官方博客））。Letta 1.0 正式发布仅见第三方 callsphere.ai（2026-04，社区来源，**未交叉验证**）。

**4. 记忆工具链与基线**
- mem0 v1.0.0（约 2025-10，官方仓库）；OpenMemory MCP（2025-05-12，官方仓库）。
- ChatDev Experiential Co-Learning（2024-01 集成，学术基线）：把失败经验沉淀进提示词供后代复用（GitHub/arXiv，社区/学术来源）。
- Google AgentKit 官方一手来源未能与同名 OpenAI AgentKit 明确区分，**数据不足**。

**对 v0.6.0 的启示**
- 项目共享上下文的正确架构 = **短期会话状态（checkpointer 类）+ 跨线程长期记忆（store 类）双层分离**；v0.6.0 看板若把全部上下文塞进单一会话会重蹈早期框架覆辙。
- 「SOP 提炼 + 自我改进」已有产品先例（CrewAI 五操作 + `learn=True` 人工反馈闭环）：v0.6.0 可在 P2 把「项目经验沉淀」做成差异化，而不只是日志归档。
- 记忆必须有**遗忘、冲突合并、自编辑**能力（CrewAI forget/矛盾检测、Letta self-editing）；只做 append-only 知识库会随项目变长而劣化。

- OpenAI/Anthropic SDK 保持薄框架路线，多平台安装包（v0.6.0 候选）应把它们作为可插拔执行后端而非竞品，重点放在安装体验与后端适配层。

## 最强竞品清单（按「项目层管理成熟度」排序 Top 5）

1. **LangChain / LangSmith Platform** — threads+assistant 版本+RBAC+workspaces+托管部署+项目级限额告警最齐全，是「项目=多会话+共享上下文」最成熟的商用实现。
2. **CrewAI AMP** — 组织级 Agent Operations 平台（Studio+RBAC+审计日志+企业审批队列），项目运营与 HITL 一体化程度最高。
3. **Microsoft Agent Framework（MAF）1.0** — 统一 SK+AutoGen 并叠加 Foundry Harness/Hosted Agents 托管与 A2A 互操作，企业生态整合力最强。
4. **Google ADK + A2A + Vertex Agent Engine** — 掌握跨组织 agent 互操作协议标准（A2A）并配套托管引擎，项目/组织边界管理有协议级优势。
5. **AWS Strands + AgentCore** — 四原语编排清晰且与 AWS 部署/治理栈原生绑定，云上项目化部署最顺滑。

补充说明：**OpenAI Agents SDK** 编排原语优秀（sessions/handoffs/approval）但项目层治理能力薄弱，定位为「可插拔执行后端」而非项目层平台竞品。
